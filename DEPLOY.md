# Deploying

Two pieces go live: the **Supabase backend** (database, sign-in, storage, live
updates, the server functions) and the **React frontend** (a static build, hosted
on Railway out of the box).

## 1. Supabase backend

1. Link the project and create the database:
   ```bash
   supabase link --project-ref <your-project-ref> && supabase db push
   ```
2. Set the model key and deploy the functions:
   ```bash
   supabase secrets set OPENROUTER_API_KEY=sk-or-... && supabase functions deploy
   ```
3. Copy the **Project URL** and **anon/publishable key** from Project Settings →
   API — the frontend needs both.

Optional secrets: `OPENROUTER_MODEL` and `OPENROUTER_EFFORT` (fallbacks only — the
model each part of the system uses is a setting inside the app), and `FORGE_PAT` if
you want to deploy functions from inside the app rather than by pushing.

## 2. Frontend on Railway

Railway builds the app and serves the static output; the configuration is already
in `railway.json` and the `start` script.

1. **New Project → Deploy from GitHub repo** → this repo, `main`.
2. Add service variables `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`. They are
   read at **build** time, so they must exist before the first build.
3. Deploy. Railway installs, builds, and serves `dist/` on `$PORT` with SPA
   fallback.
4. Add the deployed URL to Supabase **Authentication → URL Configuration** (Site
   URL and Redirect URLs), or magic links and confirmation emails will send people
   to localhost.

## 3. Keeping it up to date

After the one-time setup, pushing to `main` updates everything:

- the frontend rebuilds on Railway,
- changed server functions redeploy,
- and pending migrations are applied to the database.

That last step needs two repository secrets, because applying migrations connects
straight to Postgres:

| Secret | What it is |
| --- | --- |
| `SUPABASE_ACCESS_TOKEN` | A Supabase personal access token (Account → Access Tokens). |
| `SUPABASE_DB_PASSWORD` | The project's database password (Project Settings → Database). |

The project reference has a default and can be overridden with a repository
variable, `SUPABASE_PROJECT_REF`.

Hosted workspaces are updated together from the `release` branch, so a customer
never ends up running new frontend code against a database that has not caught up.

## Notes

- **Add variables before the build, not after.** If you add a `VITE_*` variable
  later, trigger a redeploy so it gets baked in.
- **The OpenRouter key lives only as a Supabase secret** — never in Railway, never
  in the bundle.
- **Functions generated by Forge are not in git.** They live in the database and
  are redeployed from their stored source, from inside the app.
- **A brand-new Supabase project can lag on storage.** If the first push fails on a
  storage object, wait a moment and run it again.
